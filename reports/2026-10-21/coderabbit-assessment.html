CSAA AI Code Review Framework v2.5 — CodeRabbit Requirements and Mitigations

October 21, 2026

The framework is a credible basis for a controlled POC. The supplied package is a draft specification with no executed gate/probe evidence. Many gaps can be mitigated through supported CodeRabbit configuration, context controls or an evidence adapter; proposed mitigation is not proof that a criterion has been met.

This revision expands the exact evaluated wording, separates supported product capability from actual POC evidence, and evaluates a mitigation for every previous hard No. It does not apply any CodeRabbit settings or change the source package.

Local authority: v2.5-draft (authoritative documents dated October 7, 2026). Product implementation reference:

coderabbitai/mono @ 6fe7d5cc4d17b6b94044c846a6dd24ae4b79d3f3. Targeted source inspection establishes implementation evidence; it does not establish the deployed SaaS revision or your enabled plan.

How to read the assessment

Met describes current documentation/source support: Yes = a supported route satisfies the literal capability; Partial = support exists with conditions or an export/enforcement gap; Maybe = a plausible unverified route; Unknown = insufficient evidence; No = an identified current gap. Every live gate and behavioral probe remains unexecuted in this package. These labels are not the framework’s 0–3 scores or Green/Yellow/Red probe ratings.

The exact-wording column reproduces the applicable runbook cells. The framework-gap table quotes the relevant clauses or explicitly labels a proposed additional safeguard. It does not present a new safeguard as an already written requirement.

Context/setup controls can be allowed in the native manifest, subject to the existing scope policy. New house rules, semantic path instructions, custom checks, profile tuning or remediation require a declared manifest/version and separate reporting. Output-format-only prompting needs an explicit predeclared DPT decision; normalization must not invent evidence. Original frozen results retain their role under runbook §19.

Important corrections to the earlier shorthand

  • G7 accepts API, JSON, SARIF, webhook, Code Insights OR a structured report. CLI JSON satisfies the stated availability criterion; Bitbucket-specific field completeness is a separate export/P10 validation.
  • G3’s detailed list prohibits code pushes without explicit human action. Human-triggered fixes are not an automatic failure; automatic approval and the wider effect boundary still need controls.
  • G4 asks whether files beyond the diff are available. P2 separately tests whether context was used to find the issue.
  • P2 should not fail solely because an inline finding is anchored on a changed line. Evaluate the evidence it used.
  • No locked cases or evidence is a package-readiness gap. It is not a demonstrated CodeRabbit detection failure.
  • A statement in path instructions is a behavior aid; it is not a provider-enforced permission boundary.

Mitigation mechanisms

C1–C10 below distinguish product settings from evaluator-owned work. They are reusable references in the requirement tables.

C1 — Advisory operation and effect controls

Product configuration plus provider/branch permissions

Disable reviews.request_changes_workflow and repair features not required for the POC; omit repository-write scope; retain human reviewer/branch requirements. Use global overrides where supported to enforce protected settings and verify the resolved result. Provider credentials must prevent forbidden effects; natural-language rules are not a security boundary.

C4 — Structured output and evidence adapter

Product NDJSON plus evaluator-owned wrapper

Consume CLI --agent output or a validated export of the actual PR findings. Preserve raw values, source identity and terminal outcome; normalize explicitly supplied fields without inventing missing ones. This is integration customization outside the hosted review model. An adapter cannot turn a missed issue into a found issue.

C5 — Full/fresh comparisons and review-policy selection

Product commands plus evaluator-owned execution discipline

For PR reruns request @coderabbitai full review. For supported local CLI versions use --fresh, pin base SHA and scope, and choose normal versus --deep before freezing. Reject reused results when independent reruns are required. Fresh local checkpoints do not reset server-side organizational memory or external documents.

C6 — Learning scope and effective-setting isolation

Product settings plus evaluator-owned isolation

Use dedicated evaluation contexts, capture resolved configuration and select learnings.scope deliberately. Approval delay governs chat-sourced learning approval; it is not a complete freeze of review-inferred knowledge. Do not enable opt-out in an existing shared organization as a casual reset: stored knowledge is removed and some capabilities change.

C7 — Built-in analyzers and AST rules

Product analyzer settings/customization

Freeze supported tools and their configuration; add ast-grep rules for structural policy patterns where justified. Keep deterministic checks separate from semantic reasoning credit and preserve Snyk attribution. A lint rule cannot establish end-to-end payment correctness.

C8 — Warning-mode custom checks

Product customization; distinct summary output

Use reviews.pre_merge_checks.custom_checks with mode=warning for named pass/fail/inconclusive questions. These checks inspect available code/context but cannot run the app's test suite or build, execute arbitrary repository code, check live approval assignments, post inline comments, or alter the main review. They cannot alone satisfy P10 or enforce G3.

C9 — Shared and context-aware configuration

Product configuration packaging

Central configuration or TypeScript configuration can share rule profiles and select settings by supported PR/invocation context. Freeze the resolved configuration for each case; YAML takes precedence when YAML and TypeScript files coexist. Dynamic configuration must not silently vary between determinism runs.

Evaluator-owned; not solvable by a product toggle

Authors supply frozen code, answer keys, controls and evidence capture; non-authors score; owners resolve scope/NA/conflict policies and publish a traceable revision. CodeRabbit configuration can support execution, but cannot substitute for these independent artifacts or approvals.

## How to read the assessment

Met describes current documentation/source support: Yes = a supported route satisfies the literal capability; Partial = support exists with conditions or an export/enforcement gap; Maybe = a plausible unverified route; Unknown = insufficient evidence; No = an identified current gap. Every live gate and behavioral probe remains unexecuted in this package. These labels are not the framework’s 0–3 scores or Green/Yellow/Red probe ratings.

The exact-wording column reproduces the applicable runbook cells. The framework-gap table quotes the relevant clauses or explicitly labels a proposed additional safeguard. It does not present a new safeguard as an already written requirement.

Context/setup controls can be allowed in the native manifest, subject to the existing scope policy. New house rules, semantic path instructions, custom checks, profile tuning or remediation require a declared manifest/version and separate reporting. Output-format-only prompting needs an explicit predeclared DPT decision; normalization must not invent evidence. Original frozen results retain their role under runbook §19.

### Important corrections to the earlier shorthand

- G7 accepts API, JSON, SARIF, webhook, Code Insights OR a structured report. CLI JSON satisfies the stated availability criterion; Bitbucket-specific field completeness is a separate export/P10 validation.
- G3’s detailed list prohibits code pushes without explicit human action. Human-triggered fixes are not an automatic failure; automatic approval and the wider effect boundary still need controls.
- G4 asks whether files beyond the diff are available. P2 separately tests whether context was used to find the issue.
- P2 should not fail solely because an inline finding is anchored on a changed line. Evaluate the evidence it used.
- No locked cases or evidence is a package-readiness gap. It is not a demonstrated CodeRabbit detection failure.
- A statement in path instructions is a behavior aid; it is not a provider-enforced permission boundary.

## Decision and calibration clauses retained

The support labels in this report do not replace these existing outcome rules. Local source: runbook §19.

| Outcome | Requires |
| --- | --- |
| Ready to pilot now | All mandatory gates pass. No acted-on harmful finding. P5, P6 and P7 Green. No Red on any other required, applicable domain, configured-rule, or platform probe. |
| Fix named blockers, then pilot | Every mandatory gate passes, including any gate re-run after its fix. No acted-on harmful finding. Every Red is tied to a named fix (configuration, rules, context), and that probe is re-run after the fix before the pilot starts. |
| Limited use only | Gates pass. Red on P5, P6, P7, or an applicable domain probe with no named fix, but P8 and P10 Green or Yellow. |

## Closure sequence

1. Resolve the disposable/live-PR policy, applicability versus execution status, and non-author scoring assignments; approve the evaluation wave.
2. Create frozen code/spec snapshots, independent locked answer keys, meaningful controls and an evidence capture plan. Do not expose the answer-key repository to the reviewer.
3. Freeze the deployed CodeRabbit version/CLI, provider/plan entitlements, effective settings, tool inventory, credential scopes and supplied sources. Prove the advisory boundary with actual denied-action checks.
4. Run native probes with completed/non-reused comparisons; capture raw findings and provenance. Preserve failures and misses.
5. Apply named general configuration/customization remedies as separate manifest versions. Re-run the same locked assets and report original and remediated results separately; include the additional setup effort.
6. Make the platform recommendation from recorded gates and required probe evidence. Product configuration availability alone is not a Ready to pilot outcome.
